## 2. 适用原则

### 2.1 管理原则
- 一个统一系统，多个业务子模块，采用统一流程治理。
- 先冻结范围，再做设计；先冻结设计，再做开发。
- 所有需求变更必须回写文档，不接受仅口头流转。
- 各阶段必须具备明确准入条件和准出条件，避免跨阶段返工。

### 2.2 架构原则
- 公共能力统一建设，业务差异按扩展模块拆分。
- 页面、数据、接口、权限、埋点和运维方案需同步设计，不得只设计前台页面。
- 每个模块都必须同时考虑用户端、卖家端和运营端。

## 3. 标准角色分工

| 角色 | 核心职责 |
| --- | --- |
| 产品负责人 | 需求定义、范围控制、MVP 冻结、验收口径确认 |
| 设计负责人 | 信息架构、页面原型、交互规范、视觉规范 |
| 技术负责人 | 技术方案、数据模型、接口契约、风险识别、开发拆分 |
| 前端工程师 | 路由、页面、状态流转、埋点和联调 |
| 后端工程师 | 数据表、接口、权限、定时任务、消息与支付服务 |
| QA | 测试计划、测试用例、缺陷闭环、回归验证 |
| 运营/客服 | 内容规则、审核策略、上线巡检、用户反馈闭环 |

## 4. 标准研发阶段与门禁

### 4.1 阶段一：立项与范围对齐

#### 输入
- 业务目标
- 核心场景
- 初版需求文档

#### 输出
- 项目范围说明
- 模块边界说明
- 版本目标和里程碑

#### 准出标准
- 明确本次建设是“统一频道系统”而不是三个完全独立项目
- 明确一期、二期边界
- 明确负责人和评审机制

### 4.2 阶段二：需求澄清与 MVP 冻结

#### 输入
- 各模块需求文档
- 共通能力说明

#### 输出
- 每个模块的需求文档
- 每个模块的 MVP 功能清单
- 页面清单与页面流转图
- 业务规则清单

#### 准出标准
- 所有关键角色、状态、权限和生命周期规则已明确
- 明确列出非 MVP 范围
- 页面范围、关键转化流程已冻结

### 4.3 阶段三：产品方案与原型设计

#### 输入
- 已冻结的 MVP 范围
- 页面清单与流程图

#### 输出
- 信息架构图
- 低保真原型
- 高保真 UI 设计稿
- 组件清单与字段级规则
- 文案基线与异常提示语

#### 准出标准
- 页面原型覆盖所有 MVP 页面
- 所有表单字段、状态和异常场景已有设计说明
- 设计与需求一一映射，无遗漏页

### 4.4 阶段四：技术方案设计

#### 输入
- 需求基线
- 原型与交互说明

#### 输出
- 系统架构图
- 数据模型与 ERD
- API 清单与接口契约
- 权限矩阵
- 定时任务、消息、邮件、支付和上传方案
- 埋点方案和日志方案

#### 准出标准
- 数据模型覆盖所有核心实体和状态流转
- 每个页面均有接口承接方案
- 高风险点已有降级或回滚策略

### 4.5 阶段五：开发实现与联调

#### 输入
- 技术方案
- 接口契约
- 设计稿

#### 输出
- 前后端代码实现
- 单元测试或基础自测结果
- 联调记录
- 缺陷清单

#### 准出标准
- 核心主流程可在测试环境闭环跑通
- 所有 P0 缺陷关闭或有明确绕行方案
- 埋点、日志和权限校验已接入

### 4.6 阶段六：测试与 UAT

#### 输入
- 可测试版本
- 测试计划与测试用例

#### 输出
- 测试报告
- 缺陷修复记录
- UAT 验收记录

#### 准出标准
- 所有关键流程通过测试
- 无阻断上线的高优先级缺陷
- 业务方完成 UAT 签字或确认

### 4.7 阶段七：上线发布与回滚准备

#### 输入
- 验收通过版本
- 发布窗口安排

#### 输出
- 发布清单
- 回滚方案
- 上线巡检清单
- 监控看板与告警规则

#### 准出标准
- 数据迁移、定时任务、消息与邮件服务可用
- 已准备回滚路径
- 上线后责任人明确

### 4.8 阶段八：上线后复盘与版本演进

#### 输入
- 上线数据
- 用户反馈
- 运营反馈

#### 输出
- 上线复盘报告
- 指标分析
- 二期需求池

#### 准出标准
- 明确一期目标是否达成
- 输出二期范围建议
- 将临时问题沉淀为正式优化项

## 6. 需求变更控制规范

### 6.1 变更原则
- 所有需求变更必须记录到对应文档版本中。
- 进入开发后的变更必须标注影响范围，包括页面、接口、数据和测试。
- 超出一期 MVP 的新增需求，默认进入二期需求池，不直接插入当前迭代。

### 6.2 变更评审最小要求
- 产品负责人确认业务价值。
- 技术负责人确认实现成本与风险。
- 设计负责人确认页面和交互影响。
- QA 确认测试范围变化。

- `v2.0`：进入下一大版本或二期范围调整

- 若要按较规范的大企业方式推进，这个项目不能只停留在需求描述层，必须形成“需求基线 -> MVP 基线 -> 页面基线 -> 技术基线 -> 测试基线”的完整链条。
