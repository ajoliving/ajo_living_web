# 服务式住宅展示与询盘平台需求文档

## 1. 项目概述

### 1.1 项目目标
建设一个面向服务式住宅的展示与询盘平台，支持“楼盘主项目 + 房型”二级结构，提供安全的会员联络机制，并通过时效管理保证房源信息有效。

### 1.2 适用场景
- 运营方或业主发布服务式住宅项目及对应房型。
- 用户浏览房源详情、设施、服务内容和租赁条件。
- 登录会员提交询盘或订房需求。

## 2. 核心业务模型

### 2.1 母子房源结构
平台需采用父子模型管理数据，适配一个住宅项目包含多个房型的业务场景。

### 2.2 主体信息（Parent）
- 住宅名称
- 详细地址
- 所属区域，采用香港 18 区标准
- 公共设施，例如健身室、游泳池、共享空间、24 小时保安
- 服务项目，例如清洁频率、更换床单服务、WiFi、水电等

### 2.3 房型信息（Child）
- 房型名称，例如行政套房、开放式套房、一房单位
- 实用面积
- 房型专属图片
- 月租金额
- 是否包含水电及管理费
- 最短租期限制

## 3. 业务规则

### 3.1 帖子生命周期
- 每个房源帖子的默认有效期为 `28 天`
- 系统每日执行定时任务，自动将过期帖子状态更新为 `Expired`
- 过期帖子需从前台搜索结果中移除

### 3.2 续期规则
- 业主可在后台对已过期帖子点击“重新发布”
- 续期成功后：
  - 有效期重置为新的 `28 天`
  - 列表页排序重新置顶

### 3.3 联络权限规则
- 所有联络功能均受会员登录墙保护
- 未登录访客不可查看或触发任何联络方式
- 电话和邮箱信息不得直接暴露在前端源码中

## 4. 用户角色

### 4.1 房源发布方
- 创建服务式住宅项目
- 配置房型信息、设施与服务清单
- 开启或关闭可选联络方式
- 接收询盘邮件和站内消息

### 4.2 潜在租客
- 浏览项目与房型详情
- 登录后联系业主或提交询盘表单
- 通过站内信保留沟通记录

### 4.3 平台系统
- 管理房源结构与有效期
- 控制会员权限与隐私保护
- 处理询盘邮件发送与消息备份

## 5. 核心功能需求

### 5.1 房源展示
- 支持项目级信息展示，包括品牌、地址、区域、设施、服务等
- 支持房型级信息展示，包括房型名称、面积、租金、租期和图片
- 支持项目下挂多个房型

### 5.2 联络方式配置

#### 必填项
- 联络电话
- 联络邮箱，用于接收系统转发的询盘邮件

#### 选填项
- WhatsApp 联系
- 站内短讯
- 询盘订房表格

### 5.3 WhatsApp 联系
- 点击后跳转 `wa.me`
- 自动带入预设消息
- 消息内容需包含楼盘名称、房型名称和页面链接

### 5.4 站内短讯
- 使用平台内置即时通讯系统
- 支持租客与房源发布方直接沟通
- 需保留会话记录

### 5.5 询盘订房表格
- 前端表单需包含：
  - 入住日期
  - 预计租期
  - 入住人数
  - 备注
- 提交后系统需将表单内容格式化并发送至业主联络邮箱
- 用户在站内信中收到一份备份记录

## 6. 数据字段要求

### 6.1 主体字段
- 住宅名称，必填
- 所属大厦或屋苑，选填，用于邻里匹配
- 地区或街道，采用下拉选择
- 公共设施，建议使用数组或标签
- 服务清单，建议使用数组或标签

### 6.2 房型字段
- 房型名称
- 实用面积
- 月租金额，必填
- 是否包含水电管理费
- 最短租期
- 房内设施，建议使用 `JSON/Array`
- 房型图片

### 6.3 管理字段
- `status`：`Active / Expired / Deleted`
- `created_at`
- `updated_at`
- `expire_at`

### 6.4 通用字段
- 多图上传
- 封面图设置
- 发布者身份，标记为“业主”或“代理人/专业卖家”

## 7. 技术要求

### 7.1 SEO 要求
- 面向“服务式住宅”“月租酒店”等关键词做 SEO 优化
- 详情页和列表页应优先采用 SSR 渲染

### 7.2 图片处理
- 支持房源大量图片加载
- 实现懒加载
- 自动压缩并优先使用 WebP

### 7.3 安全要求
- 电话和邮箱不得直接写入 HTML Source Code
- 询盘表单需具备防暴力提交机制，例如 CAPTCHA 或频率限制
- 所有联络动作仅对已登录会员开放

### 7.4 邮件可靠性
- 询盘邮件需通过 SMTP 或专业邮件服务发送
- 推荐接入 `AWS SES` 等服务，降低邮件被拦截风险

## 8. 用户流程

### 8.1 典型询盘流程
1. 访客进入楼盘页面
2. 浏览图片、设施和服务内容
3. 点击“联络业主”
4. 系统提示先登录
5. 用户完成手机号登录
6. 用户选择填写询盘表格或使用其他联络方式
7. 提交表单后，业主邮箱即时收到通知
8. 用户在站内信中收到备份记录

## 9. 验收标准

### 9.1 功能验收
- 未登录用户点击联络按钮时，应被引导至登录页面
- 过期帖子应自动从前台搜索结果中移除
- 续期后帖子恢复 28 天有效期并置顶
- 询盘邮件可稳定送达业主邮箱
- WhatsApp 预设消息应正确包含楼盘名、房型名和页面链接

### 9.2 安全验收
- 电话与邮箱不得在前端源码中明文暴露
- 询盘表单需具备有效的防刷机制

## 11. 基于参考页面的优化点

### 11.1 可借鉴的页面特征
- 参考页面清楚区分了“项目级信息”和“房型级信息”，适合母子房源模型展示。
- 详情页把房型、面积、月租、最短租期、设施服务和订房查询放在同一页面中，转化路径较短。
- 页面中强调了更新时间、货币切换和房型价格表，有利于提升信息可信度和国际用户使用体验。

### 11.2 本项目建议优化方向
- 首页或列表页建议直接展示“最低月租 + 房型数量 + 最短租期 + 核心设施”四个摘要字段，降低用户点进详情前的决策成本。
- 详情页采用“项目介绍 + 房型表格 + 设施服务 + 订房询盘面板”的信息结构，减少信息跳转。
- 房型展示建议升级为可切换卡片或表格视图，支持按房型、面积、月租和是否包水电快速比较。
- 在首屏增加“立即询盘”悬浮面板，固定显示电话、WhatsApp、询盘表单和最短租期信息。
- 增加“更新时间”与“价格说明”模块，明确价格是否含服务费、水电和税费，减少后续沟通成本。
- 增加“位置与交通”模块，例如附近地铁站、商圈、步行时间等，强化租客决策信息。
- 支持“房型收藏”“最近浏览”“发送自己邮箱”的轻量功能，提升高客单价用户的回访和比价体验。
