## 2. MVP 定义

### 2.1 一期目标
- 建立一个支持“项目主信息 + 房型子信息”的服务式住宅展示与询盘子系统。
- 打通“浏览项目 -> 查看房型 -> 登录会员 -> 提交询盘或联系发布方 -> 发布方接收邮件和站内备份”的业务闭环。
- 在统一频道体系中复用账号、上传、消息、生命周期和权限能力，重点扩展项目/房型双层数据结构和询盘能力。

### 2.2 MVP 范围原则
- 一期聚焦“能展示、能联系、能询盘、能管理、能续期”。
- 优先保障项目级与房型级信息结构清晰、会员登录墙可靠、询盘投递稳定。
- 不在一期引入复杂预订、库存、价格日历和营销自动化。

### 2.3 一期不追求的目标
- 不建设在线预订、库存锁房、支付定金和入住确认流程。
- 不建设复杂价格策略、节假日价格日历和渠道分销管理。
- 不建设高阶 CRM、自动跟进和多轮营销邮件系统。

## 3. 用户角色与业务边界

### 3.1 用户角色
- 访客：可浏览项目和房型信息，不可发起任何联络。
- 注册会员租客：可发起 WhatsApp、站内消息或提交询盘表单。
- 发布方：可创建项目、维护房型、管理过期与续期并接收询盘。
- 平台运营：可审核内容、下架项目、排查询盘发送异常。

### 3.2 业务边界
- 本模块属于统一频道体系中的高信息展示、高线索转化业务模块。
- 与其他子模块共享账号、上传、消息和生命周期基础能力。
- 与其他模块不同，本模块必须支持父子房源结构、询盘表单邮件发送和站内备份机制。

## 4. MVP 成功标准

### 4.1 业务成功标准
- 用户可清晰浏览项目级信息和房型级信息。
- 登录会员可成功联系发布方或提交询盘。
- 发布方可创建项目、维护房型并管理帖子有效期。
- 系统可稳定发送询盘邮件并在站内生成备份记录。

### 4.2 交付成功标准
- 页面、接口、数据模型和测试可直接围绕本清单展开。
- 双层数据结构、联络权限和询盘可靠性具备明确验收口径。
- 一期范围与增强能力分界清晰，不把预订系统混入当前范围。

## 5. MVP 必做功能清单

### 5.1 公共能力复用

| 编号 | 功能项 | 范围级别 | 功能说明 | 验收要点 |
| --- | --- | --- | --- | --- |
| `SA-MVP-01` | 手机号注册登录 | MVP 必做 | 复用统一会员系统，支持注册、登录、登出和 Token 校验 | 未登录用户点击任何联络动作时统一跳转登录页 |
| `SA-MVP-02` | 发布者身份标记 | MVP 必做 | 发布时标记“业主”或“代理人/专业卖家” | 详情页可展示发布者身份，提高可信度 |
| `SA-MVP-03` | 多图上传与封面图 | MVP 必做 | 复用统一上传能力，支持项目图和房型图上传 | 项目封面图与房型图展示准确 |
| `SA-MVP-04` | 登录墙与隐私保护 | MVP 必做 | 电话、邮箱、WhatsApp、站内短讯和询盘表单均需登录校验 | 未登录访客不可通过前端源码或接口获取敏感联系方式 |

### 5.2 前台浏览能力

| 编号 | 功能项 | 范围级别 | 功能说明 | 验收要点 |
| --- | --- | --- | --- | --- |
| `SA-MVP-05` | 服务式住宅列表页 | MVP 必做 | 展示项目封面图、项目名称、区域、最低月租、房型数量和核心设施标签 | 列表页仅展示 `Active` 状态项目，可正常分页和排序 |
| `SA-MVP-06` | 基础搜索与筛选 | MVP 必做 | 支持关键字、区域、月租范围、最短租期、核心设施等基础筛选 | 用户筛选后结果准确，并支持重置筛选 |
| `SA-MVP-07` | 服务式住宅详情页 | MVP 必做 | 展示项目级介绍、设施服务、位置、房型列表、最短租期和联系入口 | 详情页需能同时呈现项目信息和房型信息 |
| `SA-MVP-08` | 房型信息展示 | MVP 必做 | 每个项目下可展示多个房型，包含名称、面积、月租、是否包水电和图片 | 房型切换或列表展示正确，不混淆项目级字段 |
| `SA-MVP-09` | 帖子状态展示规则 | MVP 必做 | 正确区分 `Active / Expired / Deleted` 状态 | `Expired` 项目默认不在前台结果中展示 |

### 5.3 发布、维护与续期

| 编号 | 功能项 | 范围级别 | 功能说明 | 验收要点 |
| --- | --- | --- | --- | --- |
| `SA-MVP-10` | 项目发布页 | MVP 必做 | 发布方创建服务式住宅项目，填写名称、地址、区域、设施和服务清单 | 项目级必填字段缺失时不可提交 |
| `SA-MVP-11` | 房型编辑页 | MVP 必做 | 在项目下新增或编辑房型，填写面积、月租、最短租期、图片和房内设施 | 房型信息可独立维护并与项目正确关联 |
| `SA-MVP-12` | 项目编辑页 | MVP 必做 | 发布方可编辑项目级资料、项目图片和联系配置 | 编辑成功后更新时间刷新，详情页同步更新 |
| `SA-MVP-13` | 我的项目管理 | MVP 必做 | 发布方可查看 `Active / Expired` 状态项目并执行编辑或续期 | 发布方可清晰查看有效期、房型数量和状态 |
| `SA-MVP-14` | 过期项目续期 | MVP 必做 | 发布方对过期项目执行重新发布，重置有效期为新的 28 天 | 续期成功后项目前台恢复展示，并重新前置排序 |

### 5.4 联络与询盘

| 编号 | 功能项 | 范围级别 | 功能说明 | 验收要点 |
| --- | --- | --- | --- | --- |
| `SA-MVP-15` | 电话联系方式展示 | MVP 必做 | 登录会员可查看联络电话 | 电话信息不得在 HTML Source Code 中明文暴露 |
| `SA-MVP-16` | 邮箱联系方式保护 | MVP 必做 | 邮箱仅作为后端投递用途，不直接对前台明文暴露 | 页面源码中不得直接出现邮箱地址 |
| `SA-MVP-17` | WhatsApp 联系 | MVP 必做 | 登录会员点击后跳转 `wa.me` 联系发布方 | 预设消息包含楼盘名称、房型名称和页面链接 |
| `SA-MVP-18` | 站内短讯基础版 | MVP 必做 | 租客登录后可向发布方发起基础文字会话 | 会话和消息内容可持久化存储，并显示最近消息 |
| `SA-MVP-19` | 询盘表单 | MVP 必做 | 支持填写入住日期、预计租期、入住人数和备注后提交 | 表单字段完整，提交成功后给用户明确反馈 |
| `SA-MVP-20` | 询盘邮件发送 | MVP 必做 | 系统将询盘内容格式化并发送至发布方邮箱 | 邮件发送成功率可追踪，失败时有错误日志 |
| `SA-MVP-21` | 站内询盘备份 | MVP 必做 | 用户提交询盘后，在站内消息中生成一份备份记录 | 用户可在“我的消息”中查看询盘提交记录 |
| `SA-MVP-22` | 询盘防刷 | MVP 必做 | 对询盘表单施加基础防刷机制，例如频率限制或 CAPTCHA | 短时间重复提交应被限制或拦截 |

### 5.5 生命周期、SEO 与运营后台

| 编号 | 功能项 | 范围级别 | 功能说明 | 验收要点 |
| --- | --- | --- | --- | --- |
| `SA-MVP-23` | 自动过期任务 | MVP 必做 | 系统按计划扫描过期项目并更新状态 | `expire_at < 当前时间` 的项目自动转为 `Expired` |
| `SA-MVP-24` | 内容审核与人工下架 | MVP 必做 | 运营可审核项目和房型内容，并执行下架、隐藏、恢复 | 运营操作后前台状态同步更新，并保留审计记录 |
| `SA-MVP-25` | SSR/SEO 基线 | MVP 必做 | 列表页和详情页具备基础 SSR 能力和可索引元信息 | 页面标题、描述和主要内容可被正常渲染 |
| `SA-MVP-26` | 图片优化基线 | MVP 必做 | 支持懒加载、压缩和优先 WebP 展示 | 首屏图片加载合理，详情页不会因大图导致严重卡顿 |
| `SA-MVP-27` | 邮件与询盘异常排查 | MVP 必做 | 运营可排查询盘邮件投递失败和异常记录 | 异常场景可定位并支持人工复核 |

## 7. 明确不纳入一期 MVP 的范围

- 在线预订、库存锁定和支付定金。
- 多渠道分销、渠道对账和房态同步。
- 自动 CRM、营销邮件编排和智能线索评分。
- 复杂会员等级、优惠券和动态价格策略。

## 9. 依赖与前置条件

### 9.1 依赖统一能力层
- 统一账号与登录体系。
- 统一图片上传与文件存储能力。
- 统一消息中心或站内信基础设施。
- 统一生命周期字段与软删除约定。

### 9.2 模块专属前置能力
- 项目与房型的父子数据结构设计。
- 询盘表单与邮件服务方案。
- SEO 基线和 SSR 方案。

### 9.3 前置设计产物
- 页面清单与页面流转图。
- 数据模型与表结构设计。
- API 清单、权限矩阵与邮件投递流程。
- 页面原型与字段级校验规则。

## 10. 当前结论

- 服务式住宅子模块一期 MVP 可定义为“项目展示 + 房型展示 + 会员联络 + 询盘表单 + 邮件投递 + 项目管理 + 自动过期 + 续期”。
- 本清单已经把双层数据结构、登录墙、邮件投递和询盘备份这几个关键能力明确下来，可直接作为后续技术方案和测试设计基线。
- 若按标准软件流程推进，下一步应补齐父子结构 ERD、询盘 API 契约、邮件状态机和 SEO/SSR 技术方案。
