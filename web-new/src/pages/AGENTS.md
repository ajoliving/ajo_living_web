## 成員清單
account/: 帳戶登入、忘記密碼、會員中心、個人資料與通知頁面。
building/: 大廈與住戶上下文頁面。
first/: 首次進入或初始導流頁面。
furniture/: 二手物品公開列表、詳情與相關流程。
home/: AJO Living 首頁與公開入口。
marketplace/: 二手交易、會員列表、聊天、管理端與設定頁面；不得承接所有平台功能。
notifications/: 全站通知中心頁面。
- 通知中心以「會話／通知」兩個預設展開的主導航區承載通信入口；會話區提供「訊息管理／大廈群聊」子入口，通知區提供全部通知、優惠提醒、物業消息、支付提醒及系統通知分類。會話頁固定使用左側通信導航、中間會話列表、右側聊天內容三欄布局，列表可按全部、訊息管理或大廈群聊篩選；會員中心不再保留獨立訊息管理入口。
offers/: 超市優惠與門店資料頁面。
payments/: 物業費、賬單、付款、支付紀錄與 POS 支付入口頁面。
property/: 樓盤放售列表、詳情、發布與會員頁面。
serviced-residence/: 服務住宅列表與詳情頁面。
trend/: 市場趨勢頁面。
not-found/: 404 頁面。

## 架構決策
- 本目錄只承載 page 樹；API、型別、路由、全域狀態仍分別放在 `src/httpapis`、`src/model`、`src/router`、`src/pinia` 或 `src/stores`。
- 新增頁面前先判斷主模組：帳戶、大廈、物業、通知、支付、設備、二手交易或其他明確業務域。
- 每個主要 page 保持單一入口；局部元件、彈窗、狀態協調優先收在該 page 目錄內的 `widgets/`、`modals/`、`composables/`。
- UI prompt 只作為設計與實作參考；落地前仍要讀現有頁面結構、資料流與後端 API。
- 頁面文案使用繁體中文或 English，保持正式、簡約、可執行，不加入舞台感或實作說明。
- Good Price 商品展示以 API 的獨立 `brand`、審核後 `name` 及 `subtitle` 為準；搜尋建議、列表卡、表格、詳情、關聯卡與收藏需把標題拆為「商品名稱 + 右側品牌」，規格（如克重、毫升）獨立放在下一行左對齊，分類放在更下方，且不得把品牌重複寫進規格或副標題。
- Good Price 每日 CSV 導入必須自動把名稱末段可確認的重量、容量、尺寸、數量及包裝規格寫入獨立 `subtitle`；人工審核副標題優先，歷史回填只處理最近兩個資料日。
- Good Price 商品詳情的「圖片報錯」入口對所有商品圖片狀態可用，提交 `POST /api/v1/supermarket-offers/image-reports` 的 `productCode`；後端對正規化 code 全域去重，首次及重複提交均視為成功。
- Good Price 商品詳情返回列表時必須還原原有搜尋、分類、商店、品牌、排序、分頁與視圖條件；門店價格須合併詳情價格與商品已記錄門店，不得因單一明細或有優惠篩選而隱藏其他門店。
- Good Price 商品詳情的同系列選擇只讀取 API `sameSeries` 中人工確認且實際存在的商品編號；口味／配方與包裝規格各自只顯示目前另一屬性下可切換的真實組合。切換後必須前往目標商品詳情並保留既有列表返回條件，現有同品牌及同分類區塊維持推薦用途。
- 註冊帳戶類型固定為 `personal`、`individual_agent`、`agency_company`；代理帳戶須提交對應資料並通過人工審核。未通過前可瀏覽公開頁，受保護會員操作須導向代理資料頁。
- AJO 本地帳戶登入優先於 iSmart 回退；代理帳戶處於 `pending_profile`、`pending_review` 或 `rejected` 時仍須保留 session，進入受保護會員操作時強制導向代理資料頁展示進度或拒絕原因，並必須保留登出入口。
- 登入頁只提供一個「手提電話 / 電郵 / iSmart username」帳戶輸入框，不再提供電話與通用帳戶切換；前端只提交一次統一登入請求，帳戶類型識別與 iSmart 回退由 AJO 後端處理。
- 個人帳戶註冊所選大廈、樓層及單位只代表物業綁定申請；未取得已批核大廈上下文時，「我的大廈」頁必須提供前往會員中心物業綁定面板的可用入口。
- 「我的大廈」每次進入時先刷新目前會員資料，再以已保存 `bound_building_ids` 優先載入大廈資料；名稱依次使用 iSmart 回應、POS 大廈目錄及會員社區正式名稱，等於 `building_id` 的佔位值不得當作大廈名稱顯示。
- 「我的大廈」通告選擇器必須為每個會員可見大廈顯示 POS 正式名稱；會員 POS 目錄缺少部分 ID 或只返回 ID 佔位值時，前端須以公共 POS 目錄補齊，不得因其他大廈已有名稱而提前停止補全。
- 「我的大廈」各面板不顯示重複的 English kicker；最新通告目前顯示只保留正式大廈名稱，不顯示 `building_id`。大廈資料不顯示機構、目前大廈、文件數、資料狀態及重複大廈摘要，基本欄位不顯示資料來源，並在落成年份右側顯示按目前年份計算的樓齡。
- 「我的大廈」大廈財務的管理費總覽直接顯示應收摘要與明細，不重複顯示大廈名稱、編號、類型、地址、管理資料或文件總數。
- 「我的大廈」財務報表及核數報表的「上載日期」優先顯示文件 API `created_date`，舊資料缺少該欄位時才回退 `file_date`；報表月份仍使用 `file_month`。
- 「我的大廈」申請表格頁直接顯示可下載文件列表，不顯示選擇大廈說明、機構或目前大廈摘要。
- 「我的大廈」意見提供／維修報修頁使用已綁定大廈作為提交與記錄上下文，直接顯示正式大廈名稱，不提供大廈選擇框。
- 「我的大廈」智能門禁頁直接顯示門禁列表，不重複顯示目前大廈、門禁數量、可開門數量或資料狀態摘要；列表不顯示門號及所屬大廈，缺少鏡頭時顯示「未升級」。門禁摘要的 `has_permission` 不得用於前端禁用遙距開門，所有開門請求交由實際開門 API 最終鑑權。
- 「我的大廈」視像監控頁只顯示目前大廈正式名稱及可查看鏡頭，不顯示 iCCTV、Orange Pi 名稱或其他設備身份；手機版必須讓查看與新窗口操作保持在首屏表格寬度內，不依賴橫向捲動。
- 「我的大廈」業戶帳目的目前顯示單位保留完整大廈、樓層及單位上下文；未繳賬單與繳費記錄的單位列使用 AJO 後端 POS 單位目錄把 `flat_code` 轉成緊湊的「樓層/單位」，不得顯示原始單位編碼，無正式對應時顯示 `-`。繳費記錄不顯示輸入時間或合計，只按交易時間查詢與顯示；按單位或日期返回的交易都必須把 `payment_detail_objs` 限制到目前顯示單位，再按目前結果動態提供管理費等項目類型篩選。POS 單位目錄可由後端 Redis 短時快取，前端不得直接讀取 Redis。
- 「我的大廈」由左側原生下拉入口保存目前物業；控件直接顯示目前完整「大廈 / 樓層 / 單位」，下方不重複顯示目前物業。桌面及手機均只提供 iSmart `client_building_flat_units_permissions` 已授權完整單位，選中後立即保存，不另設彈窗或確認按鈕。會員中心帳號管理沿用同一完整單位選項語義，不得拆成逐級大廈、樓層及單位選擇。保存後立即更新 `/me/profile` 與全域 session，最新通告和大廈資料即時重新載入，財務、業戶帳目、門禁及監控清除舊資料並按同一大廈重新查詢。
- 會員中心初始只載入帳號管理所需的會員 POS 大廈與授權單位資料，頁面生命週期內相同大廈的會員單位請求必須復用；授權副戶與物業綁定公共目錄只在首次進入對應面板時載入，帶 `panel=property-binding` 進入時視為已進入物業綁定面板。
- 樓盤發布身份由後端按帳戶類型與已通過代理資料決定，前端不得提供業主／代理切換或可信 `publisher_identity_type` 請求欄位；公開頁的代理公司、姓名、牌照、頭像與簽名只作發布者身份展示，樓盤聯絡人姓名直接使用逐樓盤聯絡快照，電話、WhatsApp 與 Wechat 維持受控解鎖。業主帳戶 `display_name` 不得作為樓盤聯絡人，`agent_snapshot` 的 WeChat 連結或二維碼亦不得混入樓盤聯絡區，EAA 與商業登記證只限 Staff 審核查看。
- 代理公司通過審核後可建立具樓盤刊登或管理權限的公司子帳戶；子帳戶沿用母公司已通過資料，不得修改代理公司資料或建立其他子帳戶。
- 樓盤發布頁的價格區塊標題必須跟隨租售類型顯示「售價」或「租金」；放售專用的議價基礎與面議標記不得在切換放租後進入驗證、預覽或提交資料。
- 樓盤發布頁的內容翻譯只由已登入會員明確點擊後執行，前端經 AJO 後端把繁體中文標題與單位介紹翻譯成 English；不得以 `i18n` 或瀏覽器直連第三方翻譯服務，翻譯失敗不得覆蓋現有 English 欄位。
- 樓盤發布頁的 English 標題與 English 單位介紹為選填；手動翻譯失敗或未使用翻譯不得阻止發布，繁體中文標題、繁體中文單位介紹及 English 地址維持必填。
- 樓盤發布頁的公共物業資料依次顯示區域、地區、分區、大廈名稱、中英文街名及門牌、建築與實用面積、落成年份、樓齡、座數 / 大廈、實際樓層、公開樓層、單位 / 室、座向及管理費；樓齡只可由目前年份減落成年份自動計算，單位 / 室沿用單一 `unit_name` 欄位，不得拆成語義重複的兩個輸入；住宅、車位、工商及店鋪按適用性沿用相同順序，土地隱藏不適用欄位。座向與管理費不得重複放在標題描述區。
- 樓盤填寫實際樓層時，必須在同一「物業資料」區選擇公開樓層的低層、中層或高層，並以 `floor_zone` 提交；不得依賴後端的中層回退。下方標題描述區不得重複承載樓層、單位或座向。
- 住宅樓盤欄位使用完整標籤「房間數量」與「廚房類型」；「另有無沐浴廁所」固定放在浴室／廁所數量框正下方；管理費統一放在「物業資料」最後一個輸入位置，下方標題描述區不得重複顯示。
- 樓盤搜尋卡與發佈預覽必須共用同一張卡片資料層級：最上方先顯示左對齊的分區及物業類型標籤，再依次顯示放盤標題、`分區 · 屋苑中文名 English Name`，以及可選的 `座數 · 樓層 · X室`。座數為空或 `N/A` 時隱藏；已選 `floor_zone` 時只顯示公開樓層，未選時才顯示實際樓層；繁中單位固定顯示為 `X室`。位置資料行不得回退至含 `N/A` 的舊摘要，亦不得混入房間、浴室或座向。
- 樓盤放售的住宅、車位、工商、店鋪及土地分類均保存於 `feature_tags`；搜尋卡與發布預覽必須優先顯示已選分類，再顯示細則特色標籤，避免分類因四個標籤上限而缺席。
- 業主聯絡資料的電話1與電話2各自保存電話區號及 WhatsApp 可聯絡狀態，公開詳情分別使用對應區號及號碼的 WhatsApp URL；`Wechat` 欄位統一標示為 `Wechat ID`。
- 樓盤正式發布校驗必須列出所有未完成必填欄位、標示所屬步驟並定位到具體輸入框；相片與服務式住宅各房型租金須納入同一套欄位提示。
- 樓盤圖片提交只可有一個 `is_cover=true`；明確選中的封面不受圖片排序影響，未選封面時才回退首圖。公開詳情主圖必須優先顯示封面；兼容舊資料的重複封面標記時，以最後一個封面標記恢復會員原本選擇。
- 樓盤詳情與相似樓盤推薦使用獨立失敗邊界；主詳情成功後，相似樓盤接口失敗只隱藏推薦內容，不得顯示主詳情讀取失敗。
- 會員中心修改樓盤時必須按原發佈狀態執行後續動作：樓盤放售 `active` 可只儲存修改且不扣 POINT；會員另行選擇重新發佈時，才在確認後使用重新發佈接口並按現行廣告套餐積分的一半收費。`draft` 使用發佈接口，`hidden` 或 `expired` 使用重新發佈接口；不得把已發佈樓盤再次送入草稿發佈接口。
- 會員從「我的樓盤」編輯草稿或已發佈樓盤時，編輯器必須按樓盤詳情回填原有放盤類別、廣告等級、樓盤資料、圖片與逐樓盤聯絡資料；不得用新建表單預設值或目前代理資料覆蓋既有樓盤快照。
- 樓盤發佈頁只有首次建立並明確儲存草稿時提交 `charge_draft=true` 並預扣 600 AJO Points；既有草稿及已發佈樓盤的「儲存修改」一律不扣 POINT。`draft` 編輯時可修改物業分類、地址、面積、樓層及單位等物業資料；正式發佈後的 `active`、`hidden`、`expired` 編輯時才鎖定上述資料。草稿發佈總費為 1,000 AJO Points，會員列表及確認框必須顯示後端回傳的實際未付差額；內部暫存及任何既有樓盤更新不得提交草稿收費標記。
- 會員及管理端錢包流水必須以共用 i18n 映射顯示 `biz_module` 與 `action_type`；機器碼只可作未知歷史資料的回退，既有草稿多扣退款需顯示為獨立的扣費更正流水。
